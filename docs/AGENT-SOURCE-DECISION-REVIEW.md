# Agent 信息源到调度决策：十阶段迭代记录

日期：2026-10-23。目标是让专家持续从报告中获得可追溯、能改变调度判断的内容，同时保持原有五段主线和三个根技术方向。本记录对应十个实际检查与修改阶段，不代表已经执行十次完整部署或十轮性能实验。

## 当前内容与边界

- 23个研究页面，25项资料；每条注明核验范围，包含摘要级资料和官方机制说明，不统一标为全文深读。
- 27个持续来源：热点资讯2个、学术界9个、产业界16个，严格三张总表。二级分类仅为表内行组。
- 7个公开候选采集入口；本轮64条机器关键词候选，与已核验库去重后60条待原文审阅。
- 本轮新增核验6项：Temporal队列机制、Ray节点亲和、元戎会话机制、Temporal Go 1.50.0、Ray Serve 2.59.0以及从媒体追溯的Strands Box原始发布。
- 10月17—23日的4条周选维持原样。本轮补录包含历史机制与本月较早版本，不计作本周新事件。
- 未设置定时订阅、自动全文审阅或自动发布；未验证本地或昇腾性能收益。

## 能改变决策的三点认识

1. **亲和与繁忙回退必须分开设计。** [Ray官方文档](https://docs.ray.io/en/latest/ray-core/scheduling/index.html)中的软亲和在目标健康且资源可行时仍可能等待；[元戎会话教程](https://docs.openyuanrong.org/zh-cn/latest/multi_language_function_programming_interface/advanced_tutorials/ai_agent_session.html)描述绑定、租约及恢复。它们支持建立机制基线，不能共同证明已经具备完整热点迁移策略。
2. **派发公平需要与执行成本分别计量。** [Temporal官方说明](https://docs.temporal.io/develop/task-queue-priority-fairness)的控制范围是队列分区内的待派发任务。选择公平策略前要明确希望公平的是次数、资源服务量还是任务完成机会。
3. **拒绝必须能传到任务级反馈。** [Ray Serve发布说明](https://github.com/ray-project/ray/releases/tag/ray-2.59.0)提供可配置过载响应；[Strands Box原始发布](https://aws.amazon.com/blogs/opensource/introducing-strands-box-ai-agent-sandboxes-powered-by-dogwood/)描述工具约束执行。容量不足、授权拒绝和业务结果未知必须区分，不能统一进入无限重试。

上述研究取舍是本报告基于原文的推断，不是厂商对本项目的性能承诺。具体测试与停止条件见维护源；没有执行实测。

## 持续维护方式

从 [模块维护说明](../research/agent-scheduling/README.md)运行采集和检查。每轮按“候选 → 原文核验 → 专题关联 → 条件判断 → 构建 → 发布”推进：先检查覆盖缺口和旧判断的失效触发，再决定读哪些新资料。不能按发布数量代替决策价值。

采集器只更新候选与日志；人工核验后才写入事实主表。生成页面不应重新成为手工编辑源。GitHub是唯一维护仓库，Sites是发布镜像；发布映射与线上验证按 [发布说明](AGENT-REPORT-PUBLISHING.md)记录。

后续需要跟踪的缺口包括：未配置公开feed的20个来源、当前订阅批次以外的历史信息、仅完成入口检查而未形成具体核验资料的来源，以及无法读取的版本详情。页面应持续显示这些边界，避免把“持续来源”误称为“已持续全面覆盖”。
