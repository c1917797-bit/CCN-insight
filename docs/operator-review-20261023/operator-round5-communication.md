## P2：启动页的首屏范围与正文不完全对应，边界句也容易与 NCCL 证据冲突

位置：`research/ai-infra/operator-expert-guide.json:154`；`research/ai-infra/operator-routes.json:955`；生成页 `dist/ai-infra/operators-launch-granularity.html`。

首屏“技术改变”写“分组调用、张量融合与图重放分别研究”，但实际比较分支和研究问题展开的是调用分组、张量融合、分块与优先级调度，没有形成图重放的独立机制和证据。首屏给出了正文未兑现的范围。

建议将首屏句改为：

> 改变操作怎样发起、怎样聚合或分块，以及何时提交；分组调用、张量融合与分块调度分别研究。

同时，边界仍写“分组 API 不自动等于数据融合或单次启动”。其意图是避免跨后端泛化，但本页产业证据与结论已明确 NCCL 聚合路径可以共享一次 launch，阅读时容易被理解为前后否定。建议明确后端语义：

> 接口分组的启动语义取决于后端；NCCL 受支持的聚合路径可以共享一次 launch，但不会自动把张量打包成一个数据块。聚合等待或打包也可能损害计算通信流水。改变模型并行切分或微批排程属于组合调度加速，本路线保持数据交换需求不变。

依据：现有 `nccl-groups` 来源中的 Aggregated Operations 明确说明多个通信操作可聚合为一次 NCCL launch；这与 Horovod Tensor Fusion 的 pack/unpack 不是同一种改变。[NCCL Group Calls](https://docs.nvidia.com/deeplearning/nccl/user-guide/docs/usage/groups.html)

## P2：Mooncake 的控制面／数据面解释仍含不准确的表达对象

位置：`research/ai-infra/operator-routes.json:1167`、`:1269`；生成页 `dist/ai-infra/operators-paths-buffers.html` 的产业进展和证据表。

当前句“数据传送绕过控制面的正文处理”在两个位置实际展示。“正文处理”不是此处清楚的系统概念，读者无法知道被省略的是哪一次处理或数据复制；也容易把控制面不承载大块张量理解为绕过整个控制流程。这一措辞来自上一轮建议，本轮应继续收紧。

建议两处同步替换为：

> 控制面管理连接和内存区域元数据；实际数据由所选 transport 在已注册的缓冲之间传输，路径选择还需结合内存位置与拓扑。

原有“零拷贝不等于无传输、无 CPU 控制、无完成同步”和“整套系统 goodput 不能归因于单一路径”的限制应保留。

依据：现有 `mooncake-architecture` 支持控制面与数据面分离、内存注册、transport 和拓扑选择；不支持将其简写成绕过所有控制步骤。[Mooncake Architecture](https://kvcache-ai.github.io/Mooncake/design/architecture.html)
