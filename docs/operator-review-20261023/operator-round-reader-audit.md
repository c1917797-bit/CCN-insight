# 算子 13 页：专家阅读路径独立审计

日期：2026-10-23。范围：当前 `operator_research_site.py`、`operator_codegen.py`、`operator_cannbot.py`、`operator_visuals.py`、CSS/JS、现有验证脚本和生成的 13 个活跃阅读页。只做静态/语义结构审查，不代替浏览器视觉检查，也不新增设备或论文实验。本轮唯一写入本报告；未改脚本和产品。

## 总判断

事实边界与内容完整性已有明显基础：原分类、九机制、产业/学术证据、生成横向方法、内部项目不外露的定位都已成立。现在最影响专家效率的，已不是缺章节，而是**定位工具索引太浅、教程与专题主线先后不当、证据较长而对照入口不足、图中文字在窄屏缩得过小**。现有验证善于检查“文字是否出现、引用是否存在”，但还不能证明“入口是否把人带到想看的内容”。

建议优先完成下面 10 项。前 4 项是明确可复现的功能/结构缺口；其余适合本轮内容与视觉打磨，均给出可验收条件。

## 1. 首次打开：先让专家看见四条机制，再展开 Add 教程

**位置**：计算分支 `operators-1.html`；`operator_research_site.py` 的分支循环先输出 `principles` 内完整 `render_case()`，之后才输出 `routes`。

**现象**：当前计算分支正文约 9,287 字符，其中文献约 3,133 字符。读者在机制列表前先经过 Host/Device 数据流、伪代码、模板审查、八概念、三判断、Add+RMSNorm 和四路映射。路线上方内容已经是独立小教程，初次打开容易误判“计算算子研究就是 Add 开发课”。页面顶部虽然有四个跳转，但用户需要先识别“应该跳过什么”。

**建议**：首屏后立即放四路紧凑对照（机制 / 省什么 / 代表技术 / 最重要边界），然后再保留完整 Add 教学作为“从机制看执行”的展开正文。无需折叠、无需新增页面。保证“知识地图先于案例细读”，不要删除案例。

**自动验收**：DOM 中机制目录先于 `#cannbot`；四项均可直达；四项各有一句局部判断；完整案例仍静态可见、原锚点保留。不要用原始 HTML 字节数作为正式门槛。

## 2. 定位机制：总览搜索应覆盖已有技术名与证据

**位置**：`route_index()` 的 `data-route-search` 只拼接 `title + challenge + principle`；脚本只检索这一属性。

**复现结果**：当前生成页索引中，`FlashAttention-3`、`RMSNorm`、`INT8`、`Split-K`、`FLUX`、`CacheGen`、`Mooncake` 全部为 0 匹配；这些词实际上出现在相关专题中。专家一般先记住技术名，后判断属于哪条机制，当前搜索正好不支持这一路径。

**建议**：生成索引时合入具名技术分支、产业/学术标题与机制、常见别名。仅索引，不把大段正文展示在菜单中。可建立可维护 `search_terms`，让 `FA3 / FlashAttention 3 / FlashAttention-3` 等别名准确关联；不要让同一来源的泛泛免责声明把所有机制都匹配上。

**自动验收**：上述关键词各能返回包含该技术的机制；明确不存在的关键词显示空结果；清空搜索恢复 9 项；不重新获取数据；隐藏空分组或说明该组无结果；页面不增加详情点击层级。

## 3. 阅读定位：左目录高亮识别不到嵌套目标

**位置**：JS 的 `sections = document.querySelectorAll('main > section[id]')`；目录实际还包含 `#route-*` 文章和 `#cannbot-concepts / judgments / fusion`。

**错误**：当前计算分支目录中有 7 个目标不是主层级 `section`，永远无法成为脚本选出的 `current`：三个 CannBot 小节与四条具体机制。点击可以跳转，但阅读时高亮停在“从 Add 理解执行”或“机制与研究路线”。这不是视觉偏好，是目录状态与正文位置不一致。

**建议**：以目录中的真实锚点建立观察目标，而不是限定元素类型。层级较深的目标进入视区后优先标记最具体条目；向上滚动时能恢复父章节。参考文献长页同样适用。

**自动验收**：滚动到每个目录目标，最多一个 `aria-current="location"`；具体机制与案例小节均能激活；手动跳转和返回顶部不残留旧状态；宽屏目录隐藏时脚本不报错。可使用小 DOM fixture 或实际浏览器矩形检查，无需把实现函数逐行镜像成测试。

## 4. 跨页链接：文字承诺“完整数据流”，目标却是案例末尾

**位置**：`operator_cannbot.py:route_hook()` 的链接标题“查看完整数据流与概念解释”，目标却是 `operators-1.html#cannbot-routes`。

**错误**：`#cannbot-routes` 是 Add+RMSNorm 之后的四路映射，已经越过 Host/Device 图与八概念。四个专题均存在这组不一致。现有验证反而严格要求这一目标，因此仅运行现有 PASS 不能说明链接符合阅读意图。

**建议**：若文字保持“完整数据流”，跳 `#cannbot` 或专门的数据流锚点；若希望按机制直达，则分别跳 `#cannbot-memory / tiling / pipeline` 等概念，文案写清“查看缓冲/分块概念”。案例映射另设“查看四条机制如何对应”。

**自动验收**：链接的可见名称与目标节点的主题一致；四路各自的语义目标明确；原 `#cannbot-routes` 保留兼容。更新旧回归要求，不能为保住旧断言继续保留错误定位。

## 5. 比较证据：所有关键比较表都要有窄屏阅读方案

**位置**：`cg-hardware-table` 最小宽 870px、`cg-tool-table` 900px、普通机制比较表继承最小宽 640px。五系统表已经在 ≤1000px 转为带 `data-label` 的卡片，其他表没有同等处理。

**影响**：手机上读“做法”时看不到“代价”，读“产品范围”时看不到“对生成器的意义”。专家对照是并行阅读，被横向裁切后需要来回拖动记忆对应关系。仅检查无整页溢出无法发现表格内部裁切。

**建议**：复用已做好的五系统表方案，为“做法/收益/条件”“语言/职责/支持/意义”提供窄屏记录式展示；桌面继续表格。硬件横向比较可以保留对照列，但小屏按维度堆叠并显示 GPU/NPU 标签。

**自动验收**：390px 下每个单元格的语义标签可见、同一行不失关联；640px/1024px 不出现极窄长列；tab 顺序与桌面一致；表头仍对辅助技术可用。不要仅检查 `scrollWidth == clientWidth`，它不能证明信息没有被内部横向藏住。

## 6. 看懂机制：SVG 不能只做到“两块图都放得下”

**位置**：`route_svg()` 手机 viewBox 宽 396，文字字号仍沿用宽图的 10–17。375px 屏幕扣掉正文、图框内边距后，图实际约 320px 宽，10–12 的标签会进一步缩小。

**影响**：当前 SVG 结构已不是四框占位，但窄屏可能变成“看得见形状，看不清限制条件”。两个嵌套 SVG 将左右面板上下放置，解决了裁切，没有解决字号缩放。

**建议**：为手机简化辅助小字，把必要条件移动到 HTML 图注；移动图不应复制完整宽图再缩小。关键角色、资源和依赖标签优先，装饰性字少放。每图以一种机制差异为中心，不为酷炫添加无意义运动。

**自动验收**：在390px测量可见 SVG 文字的实际屏幕字号，使用 `font-size × getScreenCTM()` 缩放比，而非仅看 CSS 声明；关键标签建议至少约12px，正文图注可独立放大；文字边界不越出面板；关闭动画仍能理解机制。

## 7. 形成判断：在首屏露出“有条件的取舍”，不要把完整结论藏到文末

**位置**：机制页已有 `hero` 核心判断、文末 `expert.conclusion`；中间依次是原理、问题、证据、比较、启示。生成页总文字约17,974字符，其中出处约5,546字符，研究判断位于12张长证据卡和工具链之后。

**影响**：核心判断通常指出方向，却没有提供“现在优先看什么、什么条件会反转”的具体信息。真正的取舍在文末，手机读者失去左侧目录后还需返回页首才能跳到结论。生成页的三条 `takeaways` 是阅读方法，也不是该领域当前判断。

**建议**：首屏后新增非常短的“当前判断”栏，使用现有结论提炼的两点：最值得借鉴的具体机制/方法，以及一个反转条件或证据缺口；完整结论仍保留文末。别再整段复制 `expert.conclusion`，也别写“快速阅读版/详细版”制造版本边界。

**自动验收**：每页首个主章节之前有明确的判断摘要和文末结论直达；摘要不与 hero 逐字重复；数据源可维护；一个长页面只有一处完整结论。移动端在阅读中有可达的章节/结论入口，不能把所有导航都留在滚动起点。

## 8. 研究启示不能四计算页都只归结到“生成工具需要什么”

**位置**：四计算机制的 `practice` 主要是“机制对开发方法的启示”，全部指向 `operators-codegen.html#practice`，之后再附 actions/metrics。

**影响**：虽然根页已纠正生成只是横向方法，但各计算专题的“研究启示”仍集中服务生成器，而不是先回答研究者在复用/分块/融合/布局上学到了什么。通信五页则先重复一段工具与条件说明，两个分支表达不对称。

**建议**：每页先给机制自身的研究取舍：“值得继续跟踪哪种做法”“反例告诉我们什么”“缺哪项证据仍不能比较”。对生成工具的意义压成末尾一个相关条目，并保持链接。保留现有 actions/metrics，但将动作列表标为“证据如何改变判断”，避免看起来是每个读者必须完成的项目待办。

**自动验收**：九页各有不同的机制启示，至少一项明确绑定具名分支/证据；横向方法仍可达，但不是前四页启示的唯一结论；不得新增本地项目排期、完成状态或设备收益承诺。

## 9. 证据卡应让读者先认出“什么级别的结果”，再读长条件

**位置**：`progress_items()` 目前只按 industry/academic 分类；结果区域绿色强调，即使内容只是“证明接口存在、未报告性能”。生成卡同样在一张卡中放机制、预算、结果、边界多段。

**影响**：专家需要先区分接口能力、合成数值实验、单核性能、模块结果、训练借鉴和整模服务；当前这些判断要从多段文字中抽取。条件很完整，却缺少扫读层。

**建议**：在完整条件与结果前增加小型证据标签或事实行：`对象层级 / 硬件 / 基线 / 核心指标 / 证据类型`。没有性能值时标明“接口能力，未报告性能”，不要以绿色大块造成已获性能增益的视觉暗示。文字与数据都保留，先做可比较的入口。

**自动验收**：证据类型来自维护字段或人工确认，不能从有无数字自动猜测；性能记录必须带基线和条件，非性能记录不显示加速徽章；作者结果与本地实测严格分开；未知值用“未报告/未摘录/不适用”准确区分。

## 10. 减少重复，让文献保留追溯而不吞掉阅读重心

**现状量化**：根总览约5,551字符，文献约3,246字符；计算分支文献约占三分之一；九机制文献多为1,400–2,400字符。每条来源固定显示审阅范围、设备范围和边界，而证据卡及结论也再讲相近的外推限制。每页独立可追溯是必要的，但这些内容不需要同样字号与容器权重。

**建议**：完整来源仍默认展开，改成紧凑书目行 + 一条真正特有的核对/限制。共用的方法声明集中在页面一处；条目保留版本、定位与特有边界。为每个引用增加返回正文的入口；目前角标点到文末后主要依赖浏览器返回，连续核对多条来源时容易失去上下文。

**自动验收**：同页来源不重复；每个角标可到源条目并返回原段；任何删减不移除来源版本/URL/关键外推边界；不存在同一通用否定句在正文连续重复多次。文字数量仅作诊断，不应设一刀切字数门槛。

## 现有验证覆盖与本轮应补的缺口

现有验证已很好地守住：13页、两分类九机制、具名分支与引用、默认展开、前台无内部310P报告、旧URL重定向、CannBot数学/数据流、5具名系统12证据、本地依赖。不要为视觉调整放宽这些约束。

但下列测试现在不存在或方向不对：

- 搜索能找到已收录的技术名/别名，而非仅证明输入框和索引存在。
- 目录所有层级目标的阅读高亮，而非只检查 href 目标有效。
- 链接名称与落点主题相符；现有 `#cannbot-routes` 断言需要随语义修正。
- 窄屏内部表格与 SVG 实际可读，而非仅宽图/手机图两份 SVG 都存在。
- 专家在案例教程之前获取机制对照，并可从长页中途到结论。
- 研究启示优先属于本机制，横向生成方法只作关联。

## 推荐五轮实施顺序

1. **定位轮**：搜索索引、嵌套目录高亮、跨页语义落点（1–4中的功能部分）。
2. **层次轮**：计算页机制先于案例、首屏判断与结论入口（1、7）。
3. **比较轮**：证据级别与紧凑事实行、研究启示回到机制本身（8、9）。
4. **视觉轮**：表格窄屏和SVG屏幕字号、卡片层级与长段阅读（5、6）。
5. **复核轮**：出处去重与返回、13页全路径复核；同时重跑原有事实/引用/分类约束（10）。

此顺序优先修真正影响获取信息的问题，不用扩大首屏装饰或加动画来替代阅读结构。
