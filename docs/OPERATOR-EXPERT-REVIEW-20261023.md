# 算子研究页面独立审查（2026-10-23）

审查范围：`operator_research_site.py`、`content/operators-research.css`、三个算子研究 JSON，以及当前 `dist/ai-infra/operators*.html` 共 13 页。仅审查与建议，未改产品、研究数据或生成页，未进行浏览器视觉验收和设备实验。下文对来源覆盖的判断以当前已登记材料为限，不构成新的文献检索结论。

## 总判断

目前具备可维护的分类、清楚的研究边界和较好的事实克制，但仍更接近“机制研究提纲”，尚未形成专家可以直接用于比较技术的一站式专题。问题集中在三处：

1. **图没有解释机制。** 9 张机制图都由四个框和箭头构成，表达的是工作步骤，没有呈现优化前后数据流、资源使用和关键路径的差别。
2. **“技术进展”缺少进展本体。** 多个条目描述怎样使用工具、怎样核实信息，而非某个具体实现采用了什么技术、在什么条件下取得什么结果。部分“学术界”内容实际只有官方文档支撑。
3. **同一结论重复，新增信息不足。** 机制页首屏、研究范围、技术进展末尾、结论和文末来源都重复边界说明；最后一章重述首屏判断，没有明确技术之间的选择关系、现有证据缺口和改变判断的条件。

建议保持“总览 → 计算/通信 → 9 个机制专题”的层次。310P 保持计算分支下的工程实践，既不占据根技术分类，也不在 9 个机制旁再增一个同级方向。当前导航方向正确。

## 二、统一阅读结构：七章可以保留，章节职责要更鲜明

首屏先回答三件事：**优化对象、成立条件、当前最值得看的技术/证据**。正文按下面的职责展开，每章不复述上一章。

| 章节 | 建议短标题 | 必须提供的信息 | 应删除的重复 |
|---|---|---|---|
| 01 | 问题与范围 | 具体开销、容易出现的负载特征、与相邻机制的分工 | 不再复述完整核心判断 |
| 02 | 机制与代价 | 一张前后对照图、一条可解释关系式、收益与新增代价 | 不再先放四步操作流程 |
| 03 | 核心难题 | 两到三个真正决定方案差异的问题，每题指出冲突变量 | 避免“是否能提高性能”之类同义问句 |
| 04 | 技术与证据 | 产业实现在前、论文研究在后，逐条标明具体方案与证据 | 不把工具使用说明充当技术进展 |
| 05 | 路线比较 | 两个以上可比较做法、各自省什么/付出什么/适用区间 | 不只列“适合/先核实”的一般性条件 |
| 06 | 工程实践 | 对照对象、观察量、预期可证伪现象；310P只是其中一个案例 | 不对每个专题都复制整套通用验收流程 |
| 07 | 结论与待解问题 | 当前优先级、不能下结论之处、什么新证据会改变判断 | 不逐字重复首屏与研究范围 |

资料依据仍在正文之后完整展开。专家查阅不应依赖折叠。

## 四、九张图应各自解释什么

所有图建议采用“相同输入与结果 → 优化前后差异 → 代价”结构。颜色固定：青色为有效数据/工作，浅灰为原路径，橙色为新增代价，虚线为依赖。未核实数值只用示意量或标注假设，不能把绘制比例表现为实测比例。

1. **数据复用：中间结果是否落外存。** 左侧画 QKᵀ → 完整中间矩阵 → softmax → PV 的外存读写；右侧画输入分块、片上在线统计和输出累积。高亮被消除的中间矩阵物化；注明精确注意力机制的示意，数值结果仍遵循浮点语义。普通读者能看出“少搬中间数据”，专家能看到“仍保留哪些状态”。
2. **分块流水：复用、并行和尾块怎样互相牵制。** 上半部用同一矩阵的两种 tile 覆盖，显示完整块和尾块；下半部画读入/计算/写回三泳道，对照串行与双缓冲。标注资源占用约束，不把所有阶段默认画成可独立重叠。
3. **融合：少掉了哪些启动和临时张量。** 同一条示意算子链（如 MatMul → 偏置 → 激活）上下对照。上图每步各自启动并写回；下图共同执行并减少物化。旁边保留“寄存器/片上存储压力上升”的代价条；不声称这条示意链在某个设备已实现。
4. **布局与低精度：表示和消费路径要分开。** 以同一个逻辑矩阵分别画连续/分块布局，另画位宽表示；三条路径对照“运行期转换”“离线预打包后复用”“融合解包与计算”。把一次性成本和每次成本分色，明确低精度文件、驻留表示、计算类型是不同层面。
5. **集合与拓扑：同一结果可有不同交换路线。** 用四个 rank 展示一种分阶段集合交换示意，并标明最终每个 rank 获得的结果。再以另一种交换组织作对照；仅在材料核实后使用 Ring/Tree 等具体算法名称和轮次。图必须说明“集合语义没变，路径/轮次变了”。
6. **消息粒度：等着合并也会付出时间。** 画三条消息不同的就绪时刻；独立发送与阈值合并两条时间线对照。显示省掉的启动、增加的等待和首个下游结果可用时刻。当前简化公式旁应写清“可兼容消息、串行基准”的假设。
7. **路径缓冲：数据在哪里经过了几次复制。** 左右对照设备缓冲 → 主机暂存 → 网络 → 目标缓冲与一种经证实可用的较短路径；首次建立、注册、稳态传输单独列层。没有目标直接访问证据时把右图标作候选路径，不能画成已支持。
8. **计算通信重叠：时间线和依赖同时存在。** 串行、仅异步提交、真正重叠三行；计算和通信各用一条泳道，标注数据就绪事件和消费依赖。再画并发争用使两者变长的情况，读者才能理解为什么“重叠更多”也可能总时间更长。
9. **传输压缩：字节变少以后，总账是否仍划算。** 上图原始消息直接传输；下图编码 → 元数据+载荷 → 解码 → 消费。用可调的示意长度解释临界关系，不给未经验证的压缩率；有损误差从编码处一路连接到归约/任务输出，而非只在角落加一个精度标签。

总览图不必再画完整四框。建议将四种开销放在一张“瓶颈 → 机制”对应图中；计算、通信分支页再以各自一张综合示意说明机制组合，机制页才展示具体前后对照。

## 五、减少生硬措辞与空话：可直接替换

| 当前措辞 | 问题 | 建议替换 |
|---|---|---|
| “研究判断：……” | 每卡重复提示词，结论显得像工作笔记 | 直接写判断句，用视觉标识区分判断，不再加前缀 |

| “关键挑战：哪些问题还没有自动解决” | 并非所有机制以自动化为问题 | “关键挑战：性能、资源与正确性的取舍” |
| “适合优先考察” | 没有说明为什么优先 | “收益更可能成立的条件” |
| “先核实这些限制” | 操作指令感强，信息分类不准 | “容易失效的条件” |
| “需要同时记录的指标：……” | 五项指标塞进一段，扫读困难 | 独立短表：观察量 / 用来判断什么 / 需要固定的条件 |
| “资料与证据范围” | 名称可以，但逐条内容太像审计记录 | 标题保留；条目用“来源类型 · 版本/日期 · 适用范围”，再列一句“已核内容/未覆盖项” |
| “本轮没有重审全部实验表” | 反复以维护者过程为中心 | 在方法说明集中一次：“论文结果按已核章节摘录；未核实的效果不纳入比较。”条目只保留具体缺口 |
| “不能说明……不能证明……不能代替……” | 连续否定削弱阅读节奏 | 改为正面判断条件，如“执行收益以完整链计时为准”“设备支持按具体 SoC 与版本核对” |
| “完整性能结论仍需匹配负载实测” | 各页反复出现，缺少局部信息 | 只写本例真正尚缺的证据，如“缺少相同 shape 下融合前后总耗时与回退比例” |
| “目标设备证据/资格” | 容易被读成认证体系 | 面向读者写“该设备上的运行记录/测试覆盖”；追溯区保留原字段含义 |
| “当前制品/强基线/完整闭环” | 单独出现比较抽象 | 首次写为“本次生成的二进制”“同版本官方或已优化实现”“从生成、重建到复测的完整流程” |

边界声明不应全部删除。建议每页保留三层且各司其职：首屏一句说明证据定位；技术条目一句限制其外推；资料区保留精确出处。不要在同一条记录重复三遍“没有真机实测”。

## 六、310P 实践页的建议重排与替换

### 1. 首屏应区分价值与成熟度

建议标题仍为 **310P 算子自动生成与优化**，副标题改为：

> 用目标配置、算法契约、块模板和分块评分组织候选实现，再由独立测试决定能否保留。现有材料是对既有代码快照的静态分析，尚无本方案的 CANN、仿真或真机运行结果。

紧接三列能力表，不用百分比：

| 层次 | 已有材料说明什么 | 尚缺什么 |
|---|---|---|
| 局部工具 | 目标查询、候选评分、构建/runner、配方应用与裁决等工具被原报告定位 | 接口一致性、当前二进制绑定、有效证据校验 |
| 流程编排 | Agent 规约描述生成顺序、调试、优化与恢复责任 | 统一可执行循环、失败恢复和重建保障 |
| 运行收益 | 已有资料定义了应该检查的指标与状态 | 匹配目标设备上的正确性、耗时和模型替换结果 |

这比“成熟度尚待验证”信息更多，也不会把规约写成已实现的软件能力。

### 2. 六项技术每项用相同的五行

**作用 → 机制 → 已有实现 → 尚缺接口 → 下一项验收。** 页码和源包相对定位仍展开，但用独立的“追溯”行，不让长代码路径与正文同权重。当前 renderer 对 `locators` 使用 `[:3]` 会遗漏部分追溯位置，至少应提供完整相对定位文本；这不需要恢复本地绝对路径。

具体可替换：

- “前检身份来自配置，不能代替设备身份” → **配置用于选择生成策略；最终测试记录还要核对实际设备型号。**
- “workflow_ready只表示流程可继续” → **流程检查通过仅表示输入已满足下一阶段要求，设备运行结果另行记录。** 原字段放追溯区。
- “P2定义、P3配置、P5 Kernel与块分解，再由P4消费块结构……” → **先确定接口和配置，再确定计算、缓冲与同步结构，最后据此生成分块与 Host 分派。** P2/P3/P5/P4 在图上作为原流程标签补充。
- “Tinner取A/B加载时间之和与Cube时间的较大值” → **评分器假设 A/B 加载与 Cube 计算可以重叠，以两者较慢的一侧估算块内时间，再按分块次数累积。** 紧接“尚未完整计入哪些成本”，避免把预测等同测量。
- “APPLIED只说明文本变换完成；verdict不负责回滚” → **配方应用完成后，还要重建、复测并决定保留或恢复；目前裁决工具只输出状态，恢复仍由编排层负责。**

### 3. 六项缺口应给出依赖顺序

建议顺序：**当前源码/二进制/执行绑定 → 时间单位和测试集合统一 → 失败恢复与重建 → 块资格与生成一致性 → 分块模型校准 → 多模式交付与扩展。**

前三项是可信运行记录的基础。未接通前不宜优先扩充模板数量或搜索候选；这一投入判断来自当前缺口依赖关系，不是设备性能结论。36 块、200 候选仅保留在技术说明中，不能作为首屏能力指标。

## 七、技术进展需要补齐的“证据槽位”

当前没有统一可比的结果表，这本身不是错误；错误在于让文字看起来已经完成技术比较。建议每条材料固定以下字段，缺项公开标记“未报告/尚未摘录/当前不适用”，三种状态分清：

| 字段 | 最少内容 |
|---|---|
| 技术是什么 | 具体算法、内核、编译变换或通信协议；不以工具名称代替 |
| 解决哪项开销 | 读取字节、启动、归约轮次、转换、暴露等待等 |
| 测试对象 | 算子/模块/完整模型，shape、dtype、设备、软件栈 |
| 对照基线 | 对照实现与版本、相同执行条件、是否含转换和准备 |
| 作者报告的效果 | 原始指标及单位；没有 TTFT/TPOT 时不硬补这些指标 |
| 数值与覆盖 | 误差口径、测试用例范围、动态/尾块与回退 |
| 本页判断 | 值得吸收的机制、证据足以支持的范围、尚不能比较什么 |
| 时间与出处 | 发布/版本日期、最后核对日期、具体章节/表格/仓库入口 |

论文作者结果和本地复现结果必须分栏。没有目标设备结果不妨碍吸收机制；也不应因此把全站每个条目都改写成 310P 支持核查。研究储备面向不同模型、硬件和后续业务选择，工程验证只是其中一层。

## 八、视觉与交互建议

本节依据 CSS 和 HTML 结构判断，具体尺寸仍需浏览器复核。

- **让技术比较成为视觉中心。** 首屏保留短引言与核心判断，紧接一个紧凑“对象 / 主要变量 / 证据状态”条。路线比较使用真正的表格，每列是同类信息；不再用两张空泛的“适合/限制”白卡代替比较。
- **拉开标题与说明的权重。** 当前 `.op-note`、`.op-boundary`、文献描述多为 12px，局部关键限制也被压小。正文建议 16px 左右、行高 1.75；决定判断的边界保留正文大小，只有版本/日期/定位等辅助信息用 12–13px。
- **约束段落行长。** 当前 `main` 在大屏可到 1650px，而多数正文没有独立行宽上限。机制解释与结论用约 60–75 个拉丁字符的阅读宽度（中文需实屏验证），图与比较表可宽展示，避免一段横贯整屏。
- **目录只有一份主操作。** 桌面左目录使用当前章节高亮，顶部仍只保留总览/计算/通信三入口；窄屏隐藏侧栏后显示横向章节导航。不要给 310P 单开同级导航项。
- **图可适配窄屏。** `.op-figure svg` 当前最小宽度 620px，手机至少 590px，读者必须横拖才能看到图的全貌。专用图在窄屏改上下对照或允许完整缩放后点选细节，关键标签保持可读；不要只把原图横向截断。
- **用编号连接图与解释。** 图中 ①数据保留、②减少写回、③新增同步等标记，正文下方只解释这些差异；不要在图里塞入所有说明。图题写具体问题，图注集中说明假设。
- **引用要能就地追踪。** 保留角标与完整文末引用，同时为引用返回正文提供定位。当前编号取 sources 在 JSON 的排列位置，后续重排可能整体变号；维护时应让每个版本的编号稳定、同源不重复。
- **减少无意义的卡片层。** `.op-route`、`.op-progress-item`、`.op-case-inline`、`.op-source-list article` 全是相似边框圆角，层层叠卡削弱重点。章节正文直接排版；保留机制图、技术对照和案例三种明确视觉组件即可。
- **边界不靠灰小字表达。** 标为“机制借鉴”“作者实验”“本地实测”“仅文档入口”等简洁状态，并附实质限制。不得用颜色暗示已验证通过，更不能用绿色替代证据内容。

## 九、下一轮验收标准

1. 读者从任意机制页首屏能说明：它省哪项开销、主要代价是什么、至少一个具体做法是什么。
2. 任意一张机制图去掉正文后，仍能解释优化前后改变了什么；九图不只是替换四个框中的文字。
3. 每个产业/学术条目能追到具体材料；未登记论文的条目不伪装成已完成学术进展总结。
4. 结论给出当前选择关系或缺口优先级，且说明哪项新证据会改变它，不能只重述“需要测试”。
5. 310P 首屏准确区分局部工具、Agent 规约和未接通环节；保留无设备运行结果边界，不把项目政策写成芯片能力限制。
6. 桌面、平板、手机分别检查图中文字、长公式、路径换行与引用跳转；“没有折叠”之外，还要避免用横向裁切变相隐藏内容。

这轮建议的重点是把已经谨慎的内容变成可比较、可记住、可据此继续研究的知识，而不是给每页添加更长的免责声明或更多装饰。
